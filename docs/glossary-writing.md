# 用語集記事の書き方（トンマナとリンクのルール）

新しい用語を書く人（人間・AIとも）は、執筆前にこれを読む。
2026-09-12制定。ニュース波SEO（話題の前に用語ページを置いておく戦略）で
追加する記事が増えるため、品質を揃えるのが目的。

## 用語の選び方（ニュース波SEO）

- 根拠は `src/app/calendar/news-headlines.json`（毎朝6:40自動更新）と
  `src/app/calendar/events.ts`（今後のイベント日程）。
- 「複数の見出しに出ている」「日付の確定した大型イベントの主題」
  「一般の人が『〇〇とは』で検索しそう」の条件を満たす語だけ書く。
- **該当がない日は書かない。** 波が無いのに増やしても薄まるだけ。
- 追加前に既存slugを必ずgrepする（別表記・別名でのカバー済みに注意）。
  実績：/glossary/gpt-6 がGPT-6報道の波で週17クリック（当時の過去最高）。

## ファクトチェック（Web検索で複数ソースの裏取りをする）

用語ページは**事典**であって、ニュース記事の書き起こしではない。

**候補選びと裏取りは別工程。** news-headlines.json（7媒体の見出し）は
「何が話題か」を知るための入口であって、裏取りの材料ではない。
見出しが1媒体にしか出ていなくても、書く価値がありそうならWeb検索の工程に進む。

- **裏取りはWebSearchツールで行う**（この環境で使えることは確認済み。
  逆にWebFetchやcurlでの記事本文の直接取得はプロキシに塞がれるドメインが多いので
  頼らない。検索結果に出る複数ソースの情報で判断する）。
- 用語について**言い回しを変えて2〜3回検索**し、独立した複数ソース
  （公式発表＋報道、または別系列の報道2媒体以上）で一致した事実だけ断定形で書く。
- **単一ソースにしか出てこない情報は、「〜と報じられています」と伝聞にするか、書かない。**
  とくに数字（価格・ベンチマークスコア・ユーザー数・売上）は裏が取れなければ載せない。
- 公式発表は一次情報として扱ってよいが、性能の自称には「自己申告」「◯◯社の測定」
  の注記を添える（既存のgpt-6の項がお手本）。
- 自分の学習知識で補う場合は、古い可能性を踏まえ「2026年◯月時点」でぼかす原則を守る。
- 検索しても裏が取れない・情報が薄い語は、**今日は書かない**と判断してよい
  （翌日以降、情報が揃ってから書くほうが良いページになる）。

## 著作権（特定の記事に寄せない）

事実そのものに著作権はないが、**記事の表現・構成・独自の例え話には著作権がある**。
以下を守れば「複数ソースから事実を集めて、自分の構成と言葉で書いた事典項目」になり、
どの記事の翻案にもならない：

- **事実は必ず複数ソースから集める**（上のファクトチェックと同じ工程。
  1本の記事だけを頼りに書くと、構成まで似るのを避けられない）。
- 構成はこのサイトの既存フォーマット（short／body／sections／faq）に従う。
  **元記事の章立て・話の順番・独自の比喩やたとえ話をなぞらない。**
- 文章は最初から自分の言葉で書く。「元記事を言い換える」発想で書かない。
- 引用が必要な場合（発言など）は短く・カギ括弧で・出典を本文中に示す。基本は使わない。
- 翻訳転載はしない（英語記事の和訳をそのまま載せるのは翻案権の侵害になる）。
- **構成の主従：ニュースは「なぜ今話題か」の一段落まで。** 残りのbody・sectionsは
  時間が経っても読める解説（それは何か・仕組み・使い方・注意点）にする。
  これは著作権対策とSEOの両方に効く（特定の1ニュースに寄りかかった構成は
  元記事に似るし、波と一緒に古びる）。

## トンマナ

- **ですます調。読者は非エンジニア。** 専門用語は本文中で最初に噛み砕く。
- **ベンダー中立・事実ベース。** 特定ベンダーを持ち上げない。ベンチマークには
  測定条件の注記を添える（例：「OpenAIのアダプタ環境での測定」）。
  このサイト自体がClaude Codeで作られている件に触れるときは、その旨を開示する。
- **不確かなことは「2026年◯月時点」とぼかす。** 提供条件・料金・性能順位は
  すぐ変わる。断定は「変わらないこと（仕組み・考え方）」だけにする。
- **読者が今日使える一言で締める。** 各sectionの最後は実務目線のまとめ
  （「〜が定石です」「〜と読むと振り回されずに済みます」）に落とす。
- 絵文字はUIに置かない（CLAUDE.mdのPhosphor方針と同じ）。

## 構成（GlossaryTerm型）

- `short`: 60〜120字の一文定義。検索結果でそのまま読まれる前提で書く。
- `body`: 2段落。①それは何か ②なぜ今話題か・どう受け止めるべきか。
- `sections`: 2〜3個。「何が変わった？」「使う前の注意点」「仕事にどう関係？」
  のような読者の疑問文で見出しを立てる。
- `faq`: 2〜3問。実際に検索されそうな聞き方で（FAQPage構造化データになる）。
- `relatedSlugs`: 実在するslugのみ（ビルドエラーにならず黙ってリンク切れになる）。
- `lastUpdated`: 追加日。`data.ts` の `GLOSSARY_UPDATED` も同じ日付に更新。
- 追加先は最新のwaveファイル（現在 `terms-wave4.ts`）。冒頭コメントの語数も更新。

## linksのルール（用語集リンクだけで済ませない）

`links` は「あわせて読みたい」カード。**用語集内リンクだけで埋めるのは禁止**。
以下の優先順で、実践コンテンツを必ず探してから書く：

1. **note記事**（`src/app/note-articles.json` をキーワードでgrep）
   — ラベルは記事タイトルそのまま。例：`Claude Coworkで業務改善を半自動化してみた`
2. **マンガ連載**（/manga/wakaru=基礎、/manga/jissen=実践、/manga/honshitsu=流行と本質）
   — ラベルは `連載「◯◯」シリーズ紹介`
3. **体験ゲーム・特設ページ**（/agent /slop /undokai /history /claude-app など。
   一覧は `src/app/sitemap.ts` 末尾の配列）
   — ラベルは `体験ゲーム：◯◯（何を体感できるか）`、/historyは `AI歴史絵巻（◯◯）`
4. **用語集**（上が無いときの補完）— ラベルは `用語：◯◇（ひとこと補足）`

**合う実践コンテンツが本当に無い場合は、無理に貼らない**（関連の薄いリンクは
かえって信頼を下げる）。/calendar や /compare が文脈に合うなら使ってよい。
なお4コマは `public/yonkoma/glossary/<slug>.png` を置けば自動で出るので
linksに書かない。4コマ自体はネタ含め人間の仕事（AIは作らない）。

## 図解（diagrams.tsx）

- 検索ボリュームが見込める語には `src/app/glossary/diagrams.tsx` にslugキーで
  SVG図解を足す（手描きイラスト `image` があればそちらが優先）。
- 箱は3〜7個。**図の中に結論を1行入れる**（caption任せにしない）。
- viewBox幅600固定・文字はfontSize 12以上。ラベルが箱に重ならないか、
  ローカルビルド＋Playwrightのスクリーンショットで目視確認する。

## 追加後の手順

1. `npm run build` が通ること（唯一の検証手段）
2. `npm run og:glossary` でOGP生成。**コミットに含めるのは新規の
   `public/og/glossary/<slug>.png` と `index.png` だけ**。
   他の再生成差分は `git checkout -- public/og/` で戻す
3. 日本語Conventional Commitsでコミット → PR作成
4. **マージは人間が確認してから**（自動タスクは絶対にマージしない）
